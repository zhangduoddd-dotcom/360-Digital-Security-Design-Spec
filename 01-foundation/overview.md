# 基础规范总览
## Foundation Overview

Keywords: foundation, principles, backend design, consistency, enterprise saas, ai readable

本文定义后台设计规范的基础原则。所有页面、组件、AI 生图和 Vue 代码生成都必须遵循这些原则。

## 1. 规范目标

本规范用于企业级 SaaS、B 端管理后台、AI 原生多智能体协作平台，目标是形成一套可直接用于 Figma 设计、前端组件开发、AI 视觉生成、Vue 代码生成和设计验收的 B 端界面标准。

## 2. 规范体系结构

这套规范不是单纯的 UI 样式集合，而是一套完整的 B 端界面设计标准。核心结构为：

```text
设计原则
  ↓
全局样式 Token
  ↓
页面架构与响应式布局
  ↓
导航与页面组织
  ↓
基础操作组件
  ↓
数据录入组件
  ↓
数据展示组件
  ↓
反馈与异常处理
  ↓
业务场景模板与验收标准
```

## 3. 规范核心价值

| 层级 | 作用 | 对界面落地的意义 |
|---|---|---|
| 全局样式 | 规定颜色、字体、栅格、投影、布局 | 保证不同页面看起来属于同一产品体系 |
| 页面架构 | 规定顶部、侧边栏、内容区、弹层等关系 | 保证页面结构稳定，不因业务复杂而混乱 |
| 导航组件 | 规定顶部导航、侧边导航、面包屑、标签页、步骤条 | 帮助用户理解“我在哪里、能去哪里、下一步是什么” |
| 数据录入 | 规定表单、输入框、选择器、日期时间、上传等 | 降低输入成本，减少错误 |
| 数据展示 | 规定表格、卡片、标签、统计数值、描述列表等 | 提高复杂信息的阅读效率 |
| 反馈机制 | 规定全局提示、通知、警告、抽屉、弹窗、空状态、异常页 | 让系统状态、操作结果和风险后果被用户及时理解 |
| 业务范式 | 规定删除、创建、更新、离开等敏感操作反馈模板 | 保证高风险操作提示一致、清晰、可追责 |

## 4. 使用方式

本规范可用于四类场景：

1. 设计前：作为页面架构、组件选型、信息层级的依据。
2. 设计中：作为 Figma 组件、页面布局、交互状态的统一标准。
3. 设计后：作为设计走查、前端验收、体验一致性检查表。
4. AI 生成界面时：作为提示词中的结构约束和视觉约束，避免生成结果“好看但不可用”。

## 5. 一致性原则

同一产品内的页面结构、组件样式、交互反馈、文案表达应保持一致。

执行要求：

- 同类页面使用同一布局骨架。
- 同类操作使用同一按钮层级。
- 同类状态使用同一颜色和提示方式。
- 同类表单使用同一标签、校验和帮助信息规则。
- 同类风险操作使用同一弹窗反馈模板。

## 6. 可适配原则

页面应适配主流屏幕分辨率和不同信息密度场景。

执行要求：

- 设计输出默认以 1440px 画板为基准。
- 适配 1920 / 1440 / 1366 / 1280 等主流分辨率。
- 内容区域使用响应式布局。
- 栅格、卡片、表格和图表应根据视窗宽度自适应。
- 侧边栏在小屏下应支持自动收起或图标态。
- 表格列过多时使用横向滚动，不强行压缩到不可读。

## 7. 可控性原则

界面需要清晰、直接、可预期，减少用户的记忆负担。

执行要求：

- 页面主任务必须明确。
- 一个操作区域只保留一个最重要的主按钮。
- 高频操作显性化，低频操作合理收纳。
- 复杂任务应拆分为步骤、分组或局部任务。
- 系统状态必须及时反馈。
- 异常、空状态、加载态不能留白或让用户猜测。

## 8. 业务安全性原则

对于安全、审批、删除、断开、禁用、覆盖、重置、发布等敏感操作，必须强化确认机制。

执行要求：

- 弹窗标题必须包含动作和对象。
- 描述必须说明操作后的结果。
- 高风险操作必须说明是否可恢复。
- 不可逆操作不得只用 Toast 提示。
- 操作前、操作中、操作后都应有清晰反馈。

高风险操作模板：

```text
标题：确定 {动作} {对象} 吗？
说明：{动作} 后 {结果}，请谨慎操作。
按钮：[取消] [确认{动作}]
```

## 9. AI 生成原则

- AI 生成页面时，必须优先保证信息架构、任务路径、状态反馈和业务安全性。
- 不建议一味追求“科技感”，真正能提升质感的是清晰的信息架构、稳定的组件体系、可预期的交互反馈和透明的 AI 结果解释。
- 生成代码时，必须同时输出 Vue 页面代码和可直接预览的 HTML 文件，除非用户明确说不需要。
- AI 输出结果必须可人工审核、可编辑、可应用，不应默认为最终结果。
